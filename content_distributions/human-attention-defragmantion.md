# Social Media Distribution: Human attention defragmentation: flow, fatigue, and AI coding

## Twitter Thread

### Hook
I'm running 4 Claude sessions at once.

3 different projects. All "in progress."

At the end of the day I can't explain what any of them actually do.

This is the attention fragmentation problem nobody talks about.

### Pain Points
Token fatigue is real:

• You can fly → you fly everywhere, even with no destination
• Model is running → you open another project
• Third project → another session
• Context switching every 15 minutes
• Reviewing diffs you don't fully understand

And the worst part: the fatigue doesn't feel acute. It's chronic. You can keep going for 12 hours.

### The Flow Problem
Traditional coding had flow.

You'd hold an entire system in your head. 4-5 hours of deep focus. Then you'd hit a wall and stop.

That wall was a circuit breaker.

With AI coding you never hit the wall. You just slowly accumulate fatigue like a factory supervisor watching machines — never tired enough to stop, never fresh enough to think clearly.

### The Fix
One project at a time. Stay in the code while the model runs.

When you touch the code — even slightly — you own it.
When you only review prompts and diffs, you're one question away from uncertainty.

The difference between 100% AI-written and 5% you-written (carefully reviewed) is everything for how sustainable this feels.

## LinkedIn Post

### Story
Last month I had four Claude sessions open at once.

Four different projects. All "in progress." All generating code.

I felt incredibly productive. The output was real. PRs were getting merged.

At the end of the week, I sat down to explain one of those projects to a colleague and realized I couldn't. I knew what it was supposed to do. I didn't know what it actually did.

### The Problem
There's a term floating around: token fatigue. The insatiable drive to use AI tools to produce more, parallelize more, ship faster.

It makes sense. When you can fly, you want to fly everywhere — even if you have nowhere to go.

But the cognitive cost is brutal.

Traditional programming had flow: deep focus, holding a complex system in your head, the meditative state where you understand every piece of what you're building. It was tiring, but it felt good. After 4-5 hours you hit a wall and stopped.

With AI coding tools, that wall is gone.

You become a supervisor watching machines. Lower cognitive load per unit of time means you can work 12, 15 hours. But you're accumulating chronic fatigue the whole time — diffuse attention spread across multiple projects, never fully present for any of them.

### The WTF Moment
I realized the problem wasn't the tools. It was how I was using them.

Leaving three agents running in parallel while I jumped between contexts meant I never deeply understood anything I was building. I was reviewing diffs and approving changes in systems I'd lost track of.

The overnight anxiety made it worse: did the agent finish? Did it go off-rails? Is there a two-word correction sitting there that would save everything?

The flow state wasn't lost. I'd just designed it out of my workflow.

### What Works
One project at a time. Stay in the source code while the model runs.

When the model finishes, you're already oriented — you've been reading what it wrote, understanding what's next. You give the next instruction from actual understanding, not from skimming a summary.

The difference between "100% AI-written code I approved" and "95% AI-written code with 5% I touched directly" isn't about code quality. It's about whether you own what you built.

When you touch the code — even small parts — you own it. When you only supervised the prompts, you're standing outside your own codebase.

### The Real Fix
In my opinion, engineers who burn out on AI coding tools aren't working too hard. They're working too diffusely — supervising too many things at once, never being fully present for any of them.

The fix isn't going back to writing everything manually. It's protecting the cognitive engagement that made the work sustainable in the first place.
